# Codebase audit — 2026-10-24

Scope: all of `app/` (≈ 7,200 lines of Python, 12 templates, CSS, 3 migrations), `deploy/`, config and the test suite at commit `175d363`.
Method: full read-through of every module, `pyflakes` + `bandit` (installed in a scratch folder, not in the project), a route-shadowing scan over all 88 routes,
and **24 runtime probes** against the real code (scratch databases; one probe against a real uvicorn server). Nothing in the repo was changed by the audit.

**Status of each finding:** *confirmed* = reproduced by running it; *by reading* = clear from the code but not run; *assumption* = depends on browser/platform behaviour I could not exercise.

| Severity | Count | Theme |

| High | 6 (7 distinct defects: H2 is two) | persona edit corrupts the prompt · saving a post un-approves it · schedule shifts by the UTC offset · every AI call freezes the app · duplicate public posts on a lost response · CSRF on the API · `init-db` hides a failed migration |

## HIGH

### H1 — Editing the persona in the dashboard corrupts the AI prompt — *confirmed*
`app/web/routes.py:1084-1085` stores `json.dumps([...])` (a **string**) into JSON columns. After one save of the Profile page, `restricted_topics` and `communication_rules` come back as strings, and the prompt template iterates them **character by character**:
```
<restricted_topics>
- [
- "
- P
- o
- l
```
The API view hides it (the response schema re-parses strings), so the dashboard and tests look fine. Effect: after Lee's first edit, the model no longer sees the real rules/restrictions (only the hard-coded "Politics … off-limits" line survives). Same class of bug that was fixed in the services during M2 and missed in this route.
**Fix:** assign the list (`profile.restricted_topics = [...]`); add a regression test that renders the prompt after a dashboard edit; repair already-corrupted rows (`json.loads` when the value is a `str`).

### H2 — Saving a post in the dashboard un-approves it, and shifts its time by the UTC offset — *confirmed*
`post_update` (`routes.py:648-705`) posts **every** field on every Save.
* **Approval lost:** a `scheduled` post saved with *no* edits becomes `draft` with `approved_at = None` (all content fields count as "edited"), so the worker silently stops posting it. Setting a planned time on an approved post through the form has the same effect (the hint says it schedules it).
* **Time shifted:** the form pre-fills `planned_publish_at.strftime(...)` in **UTC** (`post_detail.html:121`) but the handler interprets the value in `APP_TIMEZONE` (`routes.py:679-683`). With the intended `APP_TIMEZONE=Europe/London`, a `2027-07-01 12:00Z` slot shows `12:00`, and after one Save is `11:00Z` — one hour earlier on **every** save in summer time. Calendar, planner and queue also print UTC under a "times shown in <local tz>" label (`calendar.html:27`, `planner.html:81`, `posts.html:76`): a 13:00 BST slot is displayed as `12:00`.
* Unparsable or blank time text silently clears the planned time (`except ValueError: pass`).
Invisible while the clocks are on GMT (UTC = London, until late March 2027), then wrong for the whole BST season.
**Fix:** convert times to the display zone on output and back on input (one helper), send only changed fields (or treat "planned time only" as a schedule change, per PLAN §11), report unparsable input.

### H3 — Every AI call freezes the whole app — *confirmed on a real server*
`POST /generate`, `POST /posts/{id}/regenerate` (`routes.py:440, 794`) and the API `generate`/`regenerate` (`api/content.py:17, 66`) are `async def` but call the synchronous Anthropic/Mistral client (up to 120 s). With one uvicorn worker, nothing else is served meanwhile. Measured: with a 4-second generation running, `GET /health` took **3.79 s** (baseline 0.00 s). In production that also stalls `/m/{token}` (Instagram fetching a Reel), OAuth callbacks, and trips the uptime monitor. PLAN §12 said these routes must be `def`.
Same pattern, smaller scale: `POST /assets/sync` hashes every new file inside the event loop (`async def` → minutes for a first Dropbox sync), ffmpeg frame extraction runs inside the generate handlers.
**Fix:** declare these handlers `def` (threadpool) — the publish/engagement routes already are.

### H4 — Duplicate public posts after a lost response — *confirmed (mock server)*
`media_publish` succeeds at Instagram but the answer is lost (read timeout). The failure is transient → retried in 5 minutes → a **new container** is created and published: **2 public posts**. Only crash recovery (`recover_stuck_claim`) checks the saved `platform_ref` before acting; the normal retry path (`_publish_live`, `services/publishing.py:217`) never does. TikTok has the same hole for slow processing: the 60-second status poll (`tiktok.py:22`) times out → retry → a second upload to the creator's drafts (2 `init` calls observed).
**Fix:** at the start of a retry, if the previous attempt has a `platform_ref`, call `check_status` first and mark the post published if the platform says so; poll TikTok longer.

### H5 — CSRF on the API; `Origin: null` bypass on the dashboard — *confirmed (no browser); assumption: browsers attach cached Basic credentials to cross-site form POSTs*
The origin check skips every `/api` path (`main.py:178`). A cross-site page can submit a form to `…/api/v1/posts/{id}/approve` — the post was approved with an `Origin: https://evil.example` header (status changed). Same for `publish` (its body is optional), `retry`, `accounts/{id}/disconnect`, `comments/{id}/ignore`, `assets/sync`. That defeats "a human approves every post". The dashboard check also lets `Origin: null` through (`origin_host` is empty → treated as same-origin), which sandboxed iframes send.
**Fix:** apply the check to all unsafe methods whatever the path (requests without `Origin` — curl, tests — stay allowed), and reject `Origin: null`.

### H6 — `init-db` hides a failed migration and stamps the database as up to date — *confirmed*
`app/cli.py:38-43`: any exception from `alembic upgrade head` → silent `create_all()` + `stamp head`, then "Database initialized successfully!" with exit code 0. A failed upgrade of a Phase-1 database (the documented update path) therefore leaves new columns missing while alembic believes the schema is current → later "no such column" errors that `alembic upgrade` can never fix. Reproduced by making `upgrade` raise: exit 0, `stamp` called.
**Fix:** only fall back when the database has no `alembic_version` table *and* no application tables; otherwise print the error and exit non-zero.

### Checked and found sound

- **Auth matrix:** with Basic auth enabled every route returns 401 without/with wrong credentials except `/health` (intended) and `/m/{token}` (signed). `//health`, `/m/../…`, `/M/x`, `HEAD`, `OPTIONS`, `POST /m/…`, `/static/../app/config.py` all 401/404.
- **Template escaping:** hostile strings (`</textarea><script>`, `"><img onerror>`, `<svg/onload>`, `{{7*7}}`) in captions, hooks, notes, filenames, descriptions, tags, usernames, comments, errors, profile fields: no unescaped output on 14 pages. The only hit is the known L1 (`engagement.html:59` JS-in-attribute).
- **Concurrency:** 4 worker loops on one due post -> exactly one `publish()` call, status `published`. A worker session with a stale read snapshot can still write after a web commit (no `database is locked`).
- **Planner:** count per week, posting window and crash-freedom held over all 172 accepted rules (only the gap violation above).
- **State machine:** 300 random actions across approve/archive/restore/edit/variant/mark-posted/retry/publish success/failure: no stuck `publishing`, no `scheduled` without a time, no `archived` without a timestamp, no `claimed_at` left behind. (One flagged "draft with stale approved_at" was a fixture artefact: the test helper creates drafts with `approved_at` set.)
